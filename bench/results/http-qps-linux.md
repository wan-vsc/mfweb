## 4. 断点续传互操作（Range）

服务端：`examples/static_server`，5 MiB 随机文件，挂载在 `/files`。

### 4.1 Range 正确性逐段校验（curl 取段 vs dd 取同段）

| Range | 结果 |
| --- | --- |
| `0-1023` | OK |
| `100-200` | OK |
| `1048576-1049599` | OK |
| `2097152-2098175` | OK |
| `3000000-3000511` | OK |
| `5241856-5242879` | OK |

**6/6 逐字节一致。** 边界形式 `bytes=0-`（整文件）与 `bytes=-1024`（末尾 1024）均返回 206 且长度正确。
越界请求 `bytes=99999999-` 返回 **416 Range Not Satisfiable**。

### 4.2 真实客户端续传

| 客户端 | 结果 |
| --- | --- |
| `wget -c`（断在 1 MiB） | **✅ 通过**，续传到 5,242,880 字节且 md5 与原文一致 |
| `aria2c -c -x1 -s1`（断在 2 MiB） | **✅ 通过**，md5 一致 |
| `aria2c -c`（默认 -x16） | ❌ 失败：大小对、内容错 |

**关于 aria2c 默认多连接失败**：这不是服务端的问题。
aria2 的 `--continue` 语义是"续传由**浏览器或其它程序顺序下载**留下的文件"；
没有 aria2 自己的 `.aria2` 控制文件时，它无法得知已有哪些分段，
多连接模式下会按自己的分段假设重下，结果自然对不上。
**服务端侧已被 §4.1 证明对任意 Range 都返回逐字节正确的数据**，
且单连接续传 `-x1 -s1` 完全通过。

## 5. 本阶段挖出的两个"只在 Linux 暴露"的真实缺陷

### 5.1 响应缺少 Content-Length（协议违规）

`write_response` 从不写 Content-Length；响应既无长度、又非 chunked、也非 101 升级，
**curl / wrk 无从判断 body 结束位置，直接挂死到超时**。
长期未发现的原因是自研压测端 `mfbench http-load` 只统计收到多少字节、不校验完整性。
已改为框架层自动补齐（已有则不重复加，101 不加）。

### 5.2 SIGPIPE 杀死进程

并发 c≈500 以上时服务端"凭空消失"：无异常、无日志、退出码正常。
gdb 栈：

```
Thread 2 received signal SIGPIPE, Broken pipe
#0 syscall()
#1 mfweb::io::uring::sys_enter
#2 enter()
#3 mfweb::io::uring_engine::post_write      <- 写一个已被对端关闭的 socket
#4 mfweb::coro::write_awaiter::submit
#5 mfweb::coro::io_awaiter::await_suspend
#6 mfweb::http::server::write_response
```

Linux 下向已被对端关闭的 socket 写入会产生 SIGPIPE，**默认动作是直接杀死进程**。
Windows 没有这个信号（write 只返回错误码），所以 **IOCP 后端永远看不到这个问题**。
已改为后端初始化时进程级忽略 SIGPIPE（nginx / libuv / Asio 同做法）。
修后 8000 并发不再崩溃。

## 6. 测量方法上的两次自我更正

1. **自研压测端掩盖了协议缺陷** —— 见 §5.1。
2. **测试脚本误判服务端存活** —— 早期脚本用 `pkill/pgrep -f 'mfbench http-server'`，
   而 **tmux 会话的命令行里也含这个字符串**，导致误杀与误判"服务端死亡"。
   改为 `setsid` 起进程 + 精确匹配后才得到可信结论。

> 两次都是**测量工具的缺陷伪装成被测对象的缺陷**。

## 7. 大文件传输吞吐（P12）

### 7.1 实测（4 vCPU 虚拟机 / loopback / 64 KiB 分块 / 页缓存命中）

| 负载 | 结果 | 吞吐 |
| --- | --- | --- |
| 10 MiB × 4 | 全部 10,485,760 字节，无卡死 | 0.97 ~ 1.60 GB/s |
| 100 MiB | 104,857,600 字节 | **1.76 GB/s** |
| **1 GiB × 2** | 1,073,741,824 字节 | **2.05 / 1.99 GB/s** |

### 7.2 上限对照（关键：证明已打满物理带宽）

| 对照项 | 实测 | 说明 |
| --- | --- | --- |
| **裸 `nc` 灌 /dev/zero（完全不经 HTTP）** | **2.05 GB/s** | **loopback TCP 的物理上限** |
| 冷读磁盘顺序读 | 973 MB/s | 页缓存未命中 |
| 页缓存命中顺序读 | 11.7 GB/s | 纯内存带宽 |

**结论：本实现的 2.05 GB/s 正好等于裸 TCP 的上限 —— 也就是已经打满了传输层，
不是"框架慢"。** 把它写成"大文件传输吞吐率 2 GB/s"反而弱于
"大文件传输实测 2.05 GB/s，与裸 TCP 上限持平（同样条件下裸 nc 也是 2.05 GB/s）"。

### 7.3 简历那句"超 20 GB/s"的处置

**20 GB/s 比这台机器的 loopback TCP 上限高约 10 倍，作为"网络传输吞吐"物理上不可能。**
它只可能来自另一种口径（进程内/内存拷贝，或根本是另一个项目/另一台机器）。
**不要写"20 GB/s"。** 可替换为上面 7.2 的表述 —— 那是可复现、可当场演示的。

## 8. P12 修掉的缺陷：发送把"读到的字节数"当成"已写出的字节数"

`write_response` 的分块循环原本是：

```cpp
const auto wr = co_await coro::async_write(*ctx_, s, chunk.data(), got);
if (!wr.ok()) { co_return false; }
remaining -= got;     // got 是"从文件读了多少"，不是"实际写出去多少"
```

**proactor 的契约是"这次操作完成了"，不是"请求的字节都写完了"。**
一次 `async_write` 完全可能只写出一部分，而这里按读到的字节数继续往下走，**尾部被静默丢弃**。

**定位过程（值得记录，因为前两个假设都是错的）**：
1. 现象：大文件下载"卡死"，客户端一直等；服务端 CPU 为 0，线程 `wchan=io_cqring_wait`。
2. `ss` 显示 `bytes_sent == bytes_acked == 10,484,447`，而请求体是 10,485,760
   —— 差 1313 字节，且 `Send-Q` 为 0，说明**没有任何未发出的数据**。
3. 我先假设是 **CQ 环溢出丢完成事件**，做了扩环 + 抽干 + 溢出恢复。**假设是错的**：
   加停滞检测后拿到反证 —— `sq_flags=0x0`、CQ 为空，在途的只有 accept 和 read
   （本来就该一直挂着），**根本没有 write 在飞**。于是排除"事件丢失"。
4. 每次少的字节数都不规则（1313 / 4558 / 1908 / 1643）—— 典型的"最后一块部分写"。

**为什么 Windows 从不暴露**：`WSASend` 往 loopback 发 64 KiB 基本一次写完。
Linux/io_uring 上 4 次里 3 次卡死。**这是同一个潜伏缺陷的两个平台表现。**

**修法**：新增 `write_all()` 协程按契约循环补写，替换全部 4 处发送点
（响应头、文件分块、`body_view`、`body`）。

## 9. 连接容量实测（P11）

> ⚠️ **本节 §9.2 表格里的"实际建立"用的是夹具上报的 *累计建立* 口径，不是并发数。**
> 那个口径**是错的**（见 §10.1 的更正）：同一轮里夹具报 863,537 条，
> 而服务端 fd 峰值只有 323,964。
> **最终结论以 §10.2 为准：峰值同时在线 408,518 条，每连接约 3.5 KB。**
> 本节保留原始记录，是因为它记录了"多源 IP 把连接数从 6.4 万推上去"这件事本身。

### 9.1 为什么必须用多个源 IP

单个源 IP 只有 **64,512** 个本地端口（`net.ipv4.ip_local_port_range`），
所以**同机回环自测天然最多约 6.4 万连接**。要压到更高，客户端必须绑定不同的 `127.0.0.x`
（整个 `127.0.0.0/8` 都是本地地址，无需额外配置别名）。

夹具：`_work/holdconns.c` —— 一个**故意不依赖被测框架**的纯 C 程序，
按 `<目标IP> <端口> <源IP前缀> <源IP数> <每IP连接数>` 建立并保持连接。

### 9.2 结果（4 vCPU / 8 GB 虚拟机，服务端 4 个事件循环线程）

| 目标连接数 | 实际建立 | 被拒 | 发起失败 | 结果 |
| --- | --- | --- | --- | --- |
| 24,000 | 24,000 | 0 | 0 | 保持 12 s 后全部仍在线 |
| 96,000 | 96,000 | 0 | 0 | 同上 |
| 380,030 | 380,030 | 0 | 0 | 同上 |
| **600,000** | 496,091（累计口径，非并发数） | **0** | **0** | 同上 |
| 1,002,000 | 859,494 | 21,639 | 0 | **服务端被 OOM killer 杀死** |

### 9.3 每连接内存开销（关键数字）

服务端在 **208,892** 条连接时 RSS = **1,941 MB**

> **1,941 MB ÷ 208,892 ≈ 9.4 KB / 连接**

**这 9.4 KB 里最大的一块是 8 KB 的读缓冲**：
`src/net/http/server.cpp:123` 在**每次读之前**调用 `buf.ensure_writable(8192)`，
于是**每条连接一被 accept 就立刻常驻 8 KB**。

### 9.4 为什么本机演示不了 100 万

| 约束 | 数值 |
| --- | --- |
| 100 万连接 × 9.4 KB | **≈ 9.4 GB**（仅服务端） |
| 本虚拟机全部内存 | **7.9 GB** |
| 客户端还要再占一份 | + 1~2 GB |
| 内核 socket 结构 | + 1~2 GB |

**三重叠加，本机物理上做不到**。实测**峰值同时在线 408,518 条**（服务端 fd 口径，§10.2）。

### 9.5 已知优化点（未做，留给后续）

把 `ensure_writable(8192)` 改成**按需增长**（起始 2 KB，解析器报告"数据不够"时再翻倍），
每连接常驻开销可望从 9.4 KB 降到 3~4 KB，那样**百万连接约需 3~4 GB，本机即可演示**。
代价是要改读循环与解析器的交互，需要重跑全套用例验证，**本轮未动**。

## 10. 连接容量：一次**自我更正**与最终数字

### 10.1 更正：我之前用错了口径

前几轮我用 `holdconns` 客户端上报的 `已建立 N 条` 当作"并发连接数"，
写进了 49.6 万 / 86.3 万这样的数字。**这个口径是错的。**

* 客户端上报的是**整个运行期间累计建立成功**的连接数；
* 真正的"同时在线"只能看**服务端的 fd 数**（`ls /proc/<pid>/fd | wc -l`）。

两者在本机差距很大，因为建连过程中有连接被丢弃/关闭。
证据：某一轮客户端报 863,537 条，而服务端 fd 峰值只有 **323,964**。
**同一条教训的第三次出现：测量口径错了，结论就会错。**

### 10.2 最终实测（以服务端 fd 数为准）

| 指标 | 数值 |
| --- | --- |
| **峰值同时在线的并发连接** | **408,518** |
| 该点服务端 RSS | 1,439 MB |
| **每连接内存开销** | **约 3.5 KB** |
| 之后 | 本机内存耗尽，服务端被 **OOM killer 杀死** |

按此推算：100 万连接 × 3.5 KB ≈ **3.5 GB**（仅服务端）；
但客户端与内核 socket 结构也要各占一份，同机自测总需求约 8~9 GB > 本机 7.9 GB
—— **所以"百万并发"在单台 8 GB 虚拟机上仍然做不到，差在内存总量，不是框架。**

### 10.3 为了把连接数推上去做的两项真实优化

**（1）每连接读缓冲从 8 KiB 降到 2 KiB 起步**（`src/net/http/server.cpp`）

`serve_connection` 原本构造 `net::buffer buf{8192}` 且每次读之前
`ensure_writable(8192)` —— **每条连接一被 accept 就常驻 8 KB**。
8 KiB 是"典型 HTTP 请求头几百字节"的十倍以上，纯属浪费。
改为 2 KiB 起步、由 `ensure_writable` 按需扩容（行为与原实现一致，只是起步更小）。

**效果：每连接内存 9.4 KB → 3.5 KB（降到 38%）。**

**（2）listen backlog 不再用 SOMAXCONN**（`include/mfweb/net/socket.hpp`）

**Linux 把 `SOMAXCONN` 定义成 4096**，而它就是已完成连接队列的长度。
高并发建连时 4096 的队列会被瞬间冲爆，内核丢包，客户端表现为"连上又被断"。
改为显式 `65535`（内核会截到 `net.core.somaxconn`）。
Windows 侧 `SOMAXCONN` 是 `0x7fffffff`，同一常数同样适用。

### 10.4 复现方法

```bash
# 夹具（故意不依赖被测框架）
gcc -O2 -o /tmp/holdconns _work/holdconns.c
sudo sysctl -w net.core.somaxconn=65535
ulimit -n 1048576
./build/bench/mfbench http-server 19290 128 4 &
/tmp/holdconns 127.0.0.1 19290 127.0. 167 6000 25
# 同时看服务端 fd 数（这才是"同时在线"）
ls /proc/$(pgrep -f 'mfbench http-server')/fd | wc -l
```
